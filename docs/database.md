# Database Design

## Database Technology

The project uses PostgreSQL as its primary relational database.

PostgreSQL was selected because it provides:

- Relational data modeling.
- Primary keys and foreign keys.
- Constraints for data integrity.
- JSONB support for flexible event properties.
- Indexing for efficient queries.
- Reliable transaction support.

The backend communicates with PostgreSQL using the `pg` library.

SQL will initially be written directly rather than using an ORM. This helps develop an understanding of SQL and relational database design.

## Database Migrations

Database schema changes will be managed using `node-pg-migrate`.

## Current Database Scope

The first migration will create only the `websites` table.

Other tables will be introduced when their corresponding features are developed.

## Table: `websites`

Stores registered website properties.

`id`

- UUID Unique Website
- ID and primary key
  `name`
- VARCHAR(100)
- Website display name
  `domain`
- VARCHAR(255)
- Website domain
  `timezone`
- VARCHAR(100)
- Timezone used for daily analytics
  `dashboard_token_hash`
- TEXT
- Hash of the dashboard access token
  `recovery_key_hash`
- TEXT
- Hash of the recovery key
  `created_at`
- TIMESTAMPTZ
- Registration timestamp
  `updated_at`
- TIMESTAMPTZ
- Last modification timestamp

### Column Details

**`id`**

A UUID generated by the backend or database.

It serves as the Website ID used by the SDK to identify which website property is sending analytics data.

**`name`**

The display name chosen by the website owner.

**`domain`**

The domain associated with the registered website.

**`timezone`**

The website's preferred timezone.

This is important because analytics will be grouped by calendar day.

For example, a website using `Asia/Manila` should see daily analytics based on Philippine time rather than necessarily using UTC calendar boundaries.

**`dashboard_token_hash`**

Stores the hash of the dashboard access token.

The original token is generated securely and returned to the website owner during registration. It is not stored in plaintext.

**`recovery_key_hash`**

Stores the hash of the recovery key.

The recovery key is separate from the dashboard token and will be used to recover access and rotate dashboard credentials.

**`created_at`**

Records when the website property was registered.

**`updated_at`**

Records when the website property was last modified.

## Planned Future Tables

These tables are not part of the initial migration. They will be introduced as their features are developed.

### `visitors`

Stores anonymous visitor identities.

A visitor belongs to a website property.

### `sessions`

Stores individual visitor sessions.

A visitor can have multiple sessions over time.

### `events`

Stores collected analytics events, including page views and custom events.

Event properties can be stored using PostgreSQL JSONB.

### `dashboard_sessions`

Stores authenticated dashboard browser sessions.

This will support exchanging the dashboard access credential for a secure browser session, such as an HTTP-only cookie.

## Planned Relationships

```text
websites
   ├── visitors
   ├── sessions
   ├── events
   └── dashboard_sessions

visitors
   ├── sessions
   └── events

sessions
   └── events
```

These relationships will be implemented when the corresponding tables are introduced.

Foreign keys will help maintain referential integrity. Where necessary, composite foreign keys can prevent records from referencing visitors or sessions belonging to another website.

## Important Design Decisions

- Every website property has its own Website ID.
- Analytics data is associated with a website property.
- Daily analytics use the website's configured timezone.
- Credentials are stored as hashes, not plaintext.
- Event properties will use JSONB.
- Tables will be added incrementally rather than creating the entire database schema upfront.
